# DAO credit payment observer

The observer reads receipts from a DAO's receiving wallet and verifies their chain inclusion. It neither holds spending keys nor sends transactions. No live wallet or payment endpoint was contacted during implementation; validation uses injected fixture responses. A configured provider still requires operational testing before enabling real credit purchases.

## Supported source contract

The implementation was checked against official Zallet release **v0.1.0-beta.3**, commit [`987382f67e622915228686e9f956c6a9c9a7514c`](https://github.com/zcash/zallet/tree/987382f67e622915228686e9f956c6a9c9a7514c), and main commit [`522b486d2e4acea9fd8868ac8331e25abd6ec145`](https://github.com/zcash/zallet/tree/522b486d2e4acea9fd8868ac8331e25abd6ec145), reviewed on October 9, 2026. Both advertise package version `0.1.0-beta.3`. `rpc.discover` must identify Zallet at that version and advertise the required wallet methods. This is a compatibility check, not cryptographic build attestation; operators must pin and verify their deployed binary. Other versions fail closed until reviewed. [OpenRPC source](https://github.com/zcash/zallet/blob/987382f67e622915228686e9f956c6a9c9a7514c/zallet-core/src/components/json_rpc/methods/openrpc.rs).

The read-only wallet allowlist is `rpc.discover`, `getwalletstatus`, `z_getaccount`, `z_listunifiedreceivers`, `z_listtransactions`, and `z_viewtransaction`. Discovery uses account UUID, inclusive start height, a null end height, offset, and limit. This keeps historical received outputs discoverable after spending; `z_listunspent` cannot provide that property. Zallet marks transaction listing experimental and does not implement `z_listreceivedbyaddress` in the reviewed source. [Method declarations](https://github.com/zcash/zallet/blob/987382f67e622915228686e9f956c6a9c9a7514c/zallet-core/src/components/json_rpc/methods.rs), [method status](https://github.com/zcash/zallet/blob/987382f67e622915228686e9f956c6a9c9a7514c/book/src/zcashd/rpc_status.md).

## DAO account and receiver binding

`z_getaccount(account_uuid)` must return the same UUID and the exact configured UA in `addresses[].ua`. `listaddresses` groups addresses by derivation but does not provide this UUID binding. `z_listunifiedreceivers` verifies the UA against the wallet's network and supplies the Sapling address and Orchard single-receiver UA used to compare received outputs. [Account source](https://github.com/zcash/zallet/blob/987382f67e622915228686e9f956c6a9c9a7514c/zallet-core/src/components/json_rpc/methods/get_account.rs), [address serialization](https://github.com/zcash/zallet/blob/987382f67e622915228686e9f956c6a9c9a7514c/zallet-core/src/components/json_rpc/methods/list_accounts.rs), [receiver source](https://github.com/zcash/zallet/blob/987382f67e622915228686e9f956c6a9c9a7514c/zallet-core/src/components/json_rpc/methods/list_unified_receivers.rs).

The application requires a **shielded-only UA**: any `p2pkh` or `p2sh` receiver makes preflight unavailable. This is stricter than ZIP 321, to keep every supported payment identifiable by a shielded memo. Operators configure an existing Sapling/Orchard-only UA; the application does not derive or modify wallet addresses. Pools other than Sapling and Orchard, including Ironwood, are unsupported in this adapter.

For each output, receipt identity is `(network, txid, pool, outputIndex)`, where Sapling uses `output` and Orchard uses `action`. The observer also requires the DAO account UUID, `outgoing:false`, `walletInternal:false`, an exact verified receiver address, and safe integer `valueZat`. Decimal ZEC values are not used. [Output serialization](https://github.com/zcash/zallet/blob/987382f67e622915228686e9f956c6a9c9a7514c/zallet-core/src/components/json_rpc/methods/view_transaction.rs).

## Memo and invoice matching

ZIP 321 encodes memo bytes as unpadded base64url, with a maximum of 512 decoded bytes. Short memos receive zero padding; transparent destinations cannot carry a memo. The invoice service binds its opaque memo, receiver, network, and exact integer amount to an authenticated stable credit account. A payment does not prove the sender's identity. [ZIP 321](https://zips.z.cash/zip-0321).

The observer decodes the raw 512-byte hex memo with strict UTF-8, removes only trailing zero padding, and requires an exact invoice memo match. `0xF6` represents an empty memo, `0xFF` arbitrary data, and other leading `0xF5..0xFE` values are reserved; `0xF4` is not a removable memo header. Any supplied `memoStr` must agree with the raw text. Transaction-list outputs expose nullable `to_account` and interpreted `memo`; final proof always uses `z_viewtransaction`. [ZIP 302](https://zips.z.cash/zip-0302), [transaction listing source](https://github.com/zcash/zallet/blob/987382f67e622915228686e9f956c6a9c9a7514c/zallet-core/src/components/json_rpc/methods/list_transactions.rs).

## Chain and reorganization checks

A separate validating-node RPC supplies `getblockchaininfo`, `getblockhash`, and `getblock(hash,1)`. The configured network must match `chain`; headers, processed height, wallet tips, and fully scanned height must agree. Wallet `locked` must be false. Low verification progress, a stale height estimate, or initial-download flags block observation. Mainnet/testnet tip timestamps must be within twenty minutes of the server clock and no more than two minutes in the future; regtest is exempt from age checks. These are conservative application readiness checks, not a proof that a trusted node sees every peer or that reorganizations are impossible. [Wallet status source](https://github.com/zcash/zallet/blob/987382f67e622915228686e9f956c6a9c9a7514c/zallet-core/src/components/json_rpc/methods/get_wallet_status.rs), [chain RPC](https://zcash.github.io/rpc/getblockchaininfo.html).

A receipt is canonical only when the declared block is the current block at its height **and its transaction list contains the txid**. Both wallet and block confirmations must equal `tipHeight - blockHeight + 1`. Transaction membership is necessary because the reviewed Zallet implementation fetches the current block at the wallet's stored transaction height, even when transaction-index lookup finds no match. Wallet and node tips must remain unchanged through verification. [Transaction metadata source](https://github.com/zcash/zallet/blob/987382f67e622915228686e9f956c6a9c9a7514c/zallet-core/src/components/json_rpc/methods/view_transaction.rs), [block RPC](https://zcash.github.io/rpc/getblock.html).

Known txids are queried directly even if absent from current discovery, including when the fully scanned canonical tip has fallen below the invoice's creation height. Zallet permits that lower-bound query and still includes unmined transactions with a null end height. A retained orphan/unmined output is returned with `canonical:false` and zero confirmations. An explicit wallet error `-5` for the known txid is treated as fully scanned absence; other provider errors are unavailable, not evidence of a missing payment. The purchase engine handles confirmation thresholds, unique receipt assignment, expiration and credited-account freezing after reorganization. Review resolution requires an operational decision; this release has no refund or unfreeze endpoint. No adapter result alone issues credits.

RPC reads have a thirty-second total budget, six-second call timeout, sixty-four-call cap, four-MiB response cap, and one history call capped at one thousand rows. A result at that limit fails closed because completeness cannot be established. Zallet takes a separate SQLite snapshot per listing call; one call avoids omissions from changing unmined rows between OFFSET pages. Redirects and caching are disabled, and provider addresses, credentials, and error details are never returned to clients. Read-only credentials and private wallet connectivity remain operator responsibilities.
