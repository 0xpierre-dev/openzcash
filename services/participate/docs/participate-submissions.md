# Participate proposal intake

13 October 2026 · Public community publication with free demo credits

Production update: `PARTICIPATE_PUBLICATION_MODE=production` publishes new immutable community records as `PUBLISHED` / `COMMUNITY_PUBLICATION`. Credits remain free and the existing account, ownership, atomic debit and scope checks remain enforced. Committee operations and automatic anchoring of native submissions remain disabled. Apply `20261013_public_participation.sql` before activation; this changes constraints only, without rewriting legacy tests, balances or preserved files. The sections below document the original 10 October pilot implementation; their `PUBLISHED_DEMO` descriptions apply only to legacy/demo-mode records.

Open **ZCG → Participate → New proposal**. The editor runs inside the existing participation service, without leaving the OpenZcash page. **My proposals** reopens the signed-in author's saved drafts and published pilot records.

The form reuses the DAO workspace's Markdown renderer, topic labels, USD validation and visual controls. ZCG intake has no DAO membership requirement, treasury selector, voter list or voting dates. It collects a public applicant name, title, complete Markdown, USD request, topics, a required Zcash Community Forum discussion and an optional GitHub application link. The forum field remains visible; new publication requires an HTTPS topic URL on `forum.zcashcommunity.com`, including topic or individual-post links. The shared client/server schema checks the host and topic path before saving for review or debiting publication credits; it does not claim to verify the topic's authorship or availability. Private drafts may omit the link. Existing published packages are not rewritten. The grant template is adapted from the existing ZCG-based model. Markdown import requires UTF-8, a `.md`/`.markdown` extension and at most 40,000 characters; replacing existing text requires confirmation.

## Draft and publication behavior

- Browsing and composing are public. Saving requires an active permanent account, using inline email-code sign-in. A public pilot requires a verified personal account; the shared persona is local-only. Drafts are private to that account, free to save and resumable after reloading.
- **Review & submit** validates and saves the current revision, renders the public content and loads the committee's current credit balance. Publication requires an explicit public-content consent checkbox.
- The agreed price is **20 Zcred = US$5.00**, at **US$0.25 per Zcred**. The current submit action runs in the named local sandbox or the explicitly configured **public free pilot**, using an account with a demo allowance and no payment requests. Public mode additionally requires a verified personal email and the configured committee scope. It uses 20 demo units once the public package is stored. These units have no cash value.
- The compact Publication panel displays the submission price, unit conversion and free-draft policy. **How credits work** explains the free allowance and draft → review → publish flow in demo mode. During review, the official-intake and confirmed-anchor qualifications appear directly above the consent; they are not hidden only in About this pilot. A new account can claim its 25 free Zcred here without leaving the form. The explanation does not enable real payments or change any credit price.
- A native record contains the exact `proposal.md` plus `application.json`, with an immutable `NATIVE_PROPOSAL` manifest. Account IDs, email and private draft history do not enter these public files.
- Success opens the new record inline, with comments, likes, revision downloads and file verification. The record is labeled **Published in demo**, appears under **All**, and is not assigned an official ZCG review status.
- No wallet call, ZEC payment, committee intake or automatic anchor is performed by this action. The new revision shows **Not anchored** until independent chain evidence exists. The earlier 25 imported records retain their existing mainnet batch evidence.

## Deletion and author withdrawal

**Delete draft** is available in My proposals and in the saved draft editor. A confirmation is required. The active draft text is deleted without a credit charge or a public activity event. A private, immutable tombstone retains only its ID, author/scope, version and timestamps to reject stale saves and safely replay a deletion. Backups follow the operator's retention policy.

After publication, only the same active author account can **Abandon proposal**. The author supplies a public reason (10–1,000 characters) and confirms its permanence. Abandonment is final in this pilot, free of an additional charge and does not refund publication credits. It preserves the published package, existing comments, likes, revisions and signed decisions. Discussion remains available; new review rounds and further signatures are blocked, including a signature prepared before withdrawal. Historical signed receipts describe their original round; they do not replace the separate withdrawal receipt.

The proposal appears in **Abandoned**, **All**, My proposals and the committee's Closed queue. Its public reason, UTC time and downloadable receipt are available on the same page. The event is `PROPOSAL_ABANDONED`, with `AUTHOR_ACCOUNT` authority (server-checked author session, not a passkey signature), a proposal-scoped actor alias, the preserved manifest hash and the prior event hash. Email, internal account IDs and idempotency keys are excluded.

Abandonment enters the existing activity batch pipeline with comments and likes. **Recorded / awaiting an anchor**, **prepared**, **confirming** and **verified** remain separate states. Saving an event does not broadcast a transaction or prove a chain timestamp. The published proposal package and the separate activity receipt should both be retained. The downloadable `activity-verify.mjs` checks the reason's exact bytes, event hash and any batch inclusion path, and can independently check supplied chain evidence with the operator's reader/node.

Apply `prisma/upgrades/20261010_proposal_lifecycle.sql` after the intake, activity and signed-decision upgrades, then regenerate Prisma Client and restart the service. Back up the database first. The additive migration creates draft tombstones and an immutable abandonment projection; it does not rewrite published content or change balances. DELETE and PATCH on `/api/participate/proposals` use trusted origins, server-resolved scope, exact author binding and optimistic/idempotent requests. Serializable transactions coordinate save/delete/publish and abandonment/signing.

## Data and safeguards

Apply `prisma/upgrades/20261010_proposal_submissions.sql` after the existing credit/archive upgrades, then generate Prisma Client. The additive upgrade adds `ProposalSubmission` and the `PROPOSAL_SUBMISSION` ledger kind; it does not alter balances or existing archive bytes. Back up the database before application. The enum addition must commit before the subsequent transaction uses it (the supplied script works with `psql -v ON_ERROR_STOP=1 -f ...`).

`/api/participate/proposals` resolves the host from server configuration and its single committee scope from existing archives. It never accepts ownership or credit-scope selection from the caller. Private reads use `no-store`; mutations require the existing session and trusted write origin. Streamed request limits, strict input validation, per-author creation limits and a draft cap apply.

Draft versions prevent silent overwrites. Publishing binds author, draft version, content hash, price version and request key. A serializable database transaction stores the archive, updates the submission and debits/journals demo credits together. Retries return the existing result, concurrent submissions cannot overspend, and failures roll back the debit. Published submissions and archive revisions are immutable. A publication has no authority over a DAO ballot or treasury.
